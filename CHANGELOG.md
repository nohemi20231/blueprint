## 2.6 - Scope rules, one tested gate, tiers, one source for both versions
| Change | Why |
|---|---|
| Scope rules SC-1..SC-9, the `scale` setting (`business` or `personal`), the gatekeeper's SCOPE CHECK and `docs/parked.md` | These were in use in `~/.claude` but never committed; the next `./install.sh` would have deleted them |
| `install.sh` backs up any installed file that differs before replacing it | Same reason: an edit made in `~/.claude` must not be lost silently |
| One gate script for Claude Code and Copilot (`hooks/no-code-before-approval.sh`, in Python, 42 tests). Writing `APPROVAL.md` asks the user; `.claude/settings.json` can be created once and not edited before approval; the rest of `.claude/` counts as code | The old Claude hook let any agent approve its own design or switch the hook off, and without `python3` its fallback let everything through on macOS |
| Per-branch lock: once a proposal names its branch, code needs an approved proposal for the current branch | In use in `~/.claude`, now in the shared gate with tests |
| DEFERRED contract entries (K5): at the round cap both sides sign a deferral that names an open item; the part is "do not build yet" | The round cap sent open requests to `open-items.md`, and the gatekeeper then blocked the service on them every time |
| Services join tier by tier; services in one tier join in parallel, one ANSWERING call per existing owner per round, tier 1 skips gathering, impact analysis once per tier | Joining one service at a time was the slowest and most expensive part of a design |
| One service with modules is a valid result (B3); the contract steps are skipped | The process assumed several services |
| Decomposers, scout and reviewers write their own files (`proposals/`, `scout-brief.md`, `reviews/`) and return a short summary | The orchestrator was pasting their reports around, and decomposer proposals were lost on resume |
| Agents work from their files in Claude Code too; `STATE.md` no longer stores agent IDs | An agent ID from an earlier session cannot be continued |
| The orchestrator writes `STATE.md`; the scribe sets status markers (charter, contract log, ADR, impact rows), keeps open items, the decision log and `risks.md`, and audits STATE | Nobody was assigned the charter status or impact-row status; a scribe call per step added a window where STATE was stale |
| Lint script (`skills/blueprint/scripts/blueprint-lint.py`, 14 tests) runs before every gatekeeper check | Status agreement, replies to requests and supersession links need no judgment; the gatekeeper now reads for what does |
| Compliance at Checkpoint 2 lists obligations only; the full check runs at the approval gate | There are no contracts or data flows to check at the service map |
| Rules and templates are copied to `docs/architecture/kit/` in both versions; no prompt points at `~/.claude` | Home-folder paths broke project and plugin installs |
| `copilot/` agents, rulebook, templates, gate and skill are generated by `scripts/build-copilot.py`; `scripts/check.sh` and CI fail when they are stale | The two versions had already drifted |
| Templates for `decision-log.md` and `risks.md`; the ADR template has the impact list and a Supersedes line; `STATE.md` records runs and scale | These files had no template or no owner |
| Gatekeeper checks are called by name, not "Job 1-4"; checkpoints show the diagram and a plain summary, the technical summary stays in the files | The job numbers were out of order; a checkpoint could not fit on one screen |
| The skill description is narrower and has an argument hint | It could start an 11-agent design for any change to a service |

Not done: packaging the Claude Code version as a plugin. It could not be tested here, so `install.sh` stays.

## 2.5 - Runs setting, default 2
- New `runs` setting (1-4, default 2) sets how many decomposers run in parallel and the maximum gathering rounds per service. Set it with `/blueprint runs=3` or at any checkpoint; it is saved in `STATE.md`.
- Default is now 2 decomposers (A business capability and C data ownership; in Copilot, Claude and Gemini) and 2 gathering rounds, down from 3 and 4. Open requests at the cap go to `open-items.md` instead of another round.
- *Why:* designs ran too long; the user wanted faster runs with fewer checks, and the number adjustable per design.

## 2.4 - GitHub Copilot version
- New `copilot/` plugin for the GitHub Copilot app and CLI: the `/blueprint` orchestrator, the rulebook, 13 agents and the no-code gate. The repo is also a plugin marketplace (`.github/plugin/marketplace.json`).
- Cross-model review: the gatekeeper and refactor reviewer run on GPT, and the three decomposers run on Claude, GPT and Gemini.
- The orchestrator copies the rulebook and templates into `docs/architecture/kit/`, because Copilot agents cannot preload skills.
- Agents start fresh on every call and work from their files, because Copilot agents cannot be resumed.
- The gate script is written for the hook input of Copilot (app, CLI, cloud agent), VS Code and Claude Code, with tests on sample payloads. Writing `APPROVAL.md` asks the user to confirm, so no agent can approve its own design; symlinks and edits to the project lock are blocked.
- *Why:* the team uses Copilot, and a reviewer from a different model family catches what same-family reviewers miss.

## 2.3 - No code before approval
- Rules G1-G4: no code, build files or scaffolding before the user approves the architecture; agents write only to `docs/architecture/`.
- Architecture approval gate after the main services are created (gatekeeper Job 3). Cost, compliance and operator reviews run before it.
- The user's approval is saved word for word in `APPROVAL.md`, with a "do not build yet" list. A direction change revokes it.
- Optional hook `no-code-before-approval.sh` that blocks file edits outside `docs/` until approval.
- *Why:* the rule existed only in the orchestrator, agents could write anywhere, and approval was never recorded.

## 2.2 - Whoever decides, updates
- New `architecture-agent`: owns the service map, boundaries, shared-area owners and cross-service flows, plus the architecture and sequence diagrams.
- Rule T6: the decider records and updates its own diagrams; an impact list sends the rest to their owners; the gatekeeper checks every row is done.
- Rule B7: every shared area (users and login, roles, payments, notifications) has one owning agent.
- Checkpoints open with the architecture diagram. The scribe only indexes.
- Renamed the orchestrator to `/blueprint`.
- *Why:* the user wanted decision owners to keep their diagrams current and one agent owning architecture decisions.

## 2.0 - Lessons from the first session
| Change | Why |
|---|---|

## Known risks and mitigations
| Risk | Mitigation |
|---|---|
| More agents means more cost per design | Reviews only at checkpoints; round caps; smaller models for scout, cost, operator, scribe |
| Reviewers can disagree (cost vs compliance) | They report at checkpoints; the user decides; the refactor-reviewer weighs them |
| The main session still routes questions | Agents read and write files directly; independent questions go out in parallel |
| The architecture agent can become a bottleneck | It decides only system-level questions; service internals stay with service agents |
| Coding starts before internal designs are final | Contracts frozen at approval; test-first; "do not build yet" areas blocked; contract changes need re-approval |
| The hook blocks a legitimate non-code file | Allowed paths are listed in the script |
| Parallel joins write the same file at once | Services in one tier do not depend on each other; each existing owner gets one ANSWERING call per round |
| A deferred contract part gets built anyway | Both sides mark it "do not build yet"; it is listed at the approval checkpoint; the final review checks nothing was built on it |
| The lint script misreads a hand-edited file | It reports WARN instead of guessing, and the gatekeeper checks that item itself |
| A generated Copilot file is edited by hand | `scripts/check.sh` and CI fail until the source is edited instead |
| Diagrams or STATE drift from reality | Owners update in the same step; the scribe reports inconsistencies; the gatekeeper cross-checks |
| compliance-reviewer sounds like legal advice | Labelled not legal advice; high-stakes items marked "confirm with counsel" |
| Prices and the operator view are estimates | Prices sourced and dated; operator points split into evidence and assumptions to validate |
